# ADR-001: Canonical Document Model (CDM)

- **Status:** Accepted
- **Date:** 2026-07-26
- **Phase:** Phase 1 – Knowledge Ingestion

---

## Context

Knowledge Nexus is designed to ingest knowledge from multiple document formats including TXT, Markdown, DOCX, PDF, PPTX, XLSX, and images. Every document format has its own internal structure and parsing mechanism.

However, downstream components such as chunking, embeddings, indexing, retrieval, and reasoning should not depend on the original document type.

To achieve this, the system requires a common representation immediately after the parsing stage.

---

## Decision

Introduce a **Canonical Document Model (CDM)** as the standard representation for every parsed document.

Every document processor must convert its source document into the same `Document` model irrespective of the original file format.

The initial CDM consists of three models:

- `Document`
- `Metadata`
- `Content`

```text
Document
├── id
├── metadata
└── contents
      ├── Content
      ├── Content
      └── ...
```

---

## Design Decisions

### 1. A Document is a collection of Content blocks

A document is modeled as a collection of ordered content blocks rather than a single text string.

Different document formats naturally contain multiple logical units such as:

- Paragraphs
- Headings
- Lists
- Tables
- Images
- Code Blocks

Representing a document as `List[Content]` preserves the logical structure of the document while providing a consistent abstraction across all supported formats.

---

### 2. Content is a separate model

`Content` represents the smallest logical unit inside a document.

Keeping it separate from `Document` allows different parsers to represent their content uniformly while preserving document-specific structure.

Examples:

| Document Type | Content Blocks |
|--------------|----------------|
| TXT | Entire text |
| Markdown | Headings, Paragraphs, Lists, Code Blocks |
| DOCX | Paragraphs, Tables, Images |
| PDF | Text Blocks, Figures, Tables |
| PPTX | Slide Content |
| XLSX | Tables / Sheets |

Each `Content` block maintains its own:

- Type
- Text
- Order

while the `Document` acts only as the container.

This separation also follows the **Single Responsibility Principle**, where:

- `Document` represents the document itself.
- `Content` represents the individual logical units inside the document.

---

### 3. Every parser returns the same Document

Every document parser returns the same `Document` model.

This creates a common contract for downstream services.

As a result, components such as:

- Chunking
- Tokenization
- Embedding Generation
- Indexing
- Retrieval
- Agentic Workflows

operate purely on the CDM without knowing whether the source document was:

- TXT
- Markdown
- DOCX
- PDF
- PPTX
- XLSX

Without a common contract, every parser would eventually require its own implementation of downstream services such as chunking and embedding generation, leading to duplicated logic and tighter coupling throughout the system.

---

### 4. Storage is separated from parsing

Storage and parsing solve different problems.

The storage layer is responsible for:

- Uploading files
- Downloading files
- Retrieving object metadata

The parser is responsible for:

- Understanding document contents
- Converting documents into the CDM

Keeping these responsibilities separate allows the storage implementation (MinIO, Amazon S3, Local Filesystem, etc.) to change without affecting any parser implementations.

This separation also allows the same storage service to be reused across the entire platform rather than coupling it to individual parsers.

---

## Consequences

### Advantages

- Establishes a single contract for the entire ingestion pipeline.
- Keeps downstream services independent of document formats.
- Makes adding support for new document types straightforward.
- Reduces coupling between storage and parsing.
- Simplifies testing by allowing every parser to produce the same output model.
- Encourages modular system design.

---

### Trade-offs

- The CDM will evolve as richer document formats are introduced.
- Some document-specific information may require future extensions to the model.
- The initial implementation intentionally prioritizes simplicity over complete document fidelity.

---

## Initial Scope

The first implementation targets **TXT** documents.

A TXT document is represented as:

- One `Document`
- One `Metadata`
- One `Content` block of type `"text"`

The objective is not to build a feature-complete parser but to validate the parsing architecture and establish the Canonical Document Model before supporting more complex document formats.

---

## Future Considerations

The CDM is expected to evolve as additional document processors are introduced.

Potential future extensions include:

- Sections
- Pages
- Tables
- Images
- OCR Output
- Rich Metadata
- Content Type Enumeration

These enhancements should be introduced only when driven by actual requirements from new document formats rather than anticipated future needs.

---

## Rationale

The Canonical Document Model serves as the common language of the Knowledge Nexus ingestion pipeline.

By enforcing a single representation immediately after parsing, every subsequent component in the system can focus solely on its own responsibility without needing to understand individual document formats.

This decision prioritizes modularity, extensibility, and separation of concerns while keeping the initial implementation intentionally simple.
